Flat context: why an agent should never see more than two tools

Every demo in this gallery — Pizza Shop Ops, Mars Greenhouse Ops, The Squad Room, DRI On-Call Agent — makes the same trade, over and over: instead of loading every tool's schema into the model's context on every turn, load two: tool_search and call_tool. The box can hold 18 tools or 480; the agent's context stays flat. This post is the argument for why that's the right default, not just a trick for demos.

The problem with "just give it all the tools"

The obvious way to wire an agent to N tools is to hand the model N JSON schemas up front and let it pick. It works — until N grows. Every schema costs tokens on every single turn, whether or not the model uses it. A 48-tool box re-sent on every turn of a 6-turn conversation isn't 48 tools' worth of cost; it's 288 tool-loads. Worse, tool selection accuracy tends to degrade as the list grows: the model has to read past dozens of irrelevant schemas to find the one it needs, and near-duplicate tools (two things that both sound like "search") get confused for each other.

The fix: search, don't stuff

A governed Toolbox flips the model from "reads every schema" to "asks a question." tool_search takes a natural-language intent — "find the theming pattern," "gate the oven behind approval," "cut a release" — and returns the two or three tools that actually match, ranked. call_tool invokes whichever one it picked. The full catalog can keep growing on the server side; the model's context never grows with it.

>_ [agent]      "gate the oven behind an approval before it starts a bake"
   [tool_search] query: "require approval before starting an oven run"
   [matched]     oven.start, oven.status
   [call_tool]   oven.start({ ... })  => [approval required] paused for a human

The context an agent carries per turn is tool_search + call_tool — two schemas — no matter whether the box behind it holds 18 tools (Pizza Shop Ops) or 48 (The Squad Room). Add a hundred more tools to the catalog next month and nothing in the agent's prompt changes.

Governance rides along for free

Because every call funnels through call_tool, policy lives on the box, not in the agent. Mark a tool require_approval: always and it pauses for a human no matter which agent, or how many agents, are calling it — that's the whole trick behind Squad Room's shared-Toolbox team and the DRI agent's governed actions. You don't audit N agents' worth of ad-hoc tool wiring; you audit one box.

What it costs you

Honesty first: Tool Search adds a round-trip. Instead of the model deciding in one shot, it searches, gets a short ranked list, then decides. For a handful of tools that overhead isn't worth it — flat context wins as the catalog grows, not before it. And ranking quality is only as good as your tool descriptions; vague or overlapping descriptions still confuse the ranker, just fewer schemas' worth of confusion instead of dozens.

Try it

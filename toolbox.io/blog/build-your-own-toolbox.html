Build Your Own Toolbox with Tool Search

A beginner-friendly path from a few useful functions to an agent that discovers the right one when it needs it.

Start with the problem, not the tools

A toolbox is a collection of capabilities an agent can use: checking inventory, looking up a customer, creating an issue, or reading a runbook. The first step is to choose one small workflow and list the decisions the agent must make.

For example, a café assistant might need to answer: “Do we have oat milk?” That workflow needs one read-only capability: check_stock(item). Keep the first version narrow and safe.

Make each tool do one clear job

Give every tool a specific name, a short description, and a small set of inputs. A good description tells the agent when to use the tool and what it returns.

check_stock(item)
Returns the current quantity and availability of a menu ingredient.

Prefer tools that report facts before tools that change things. When you add an action such as place_order, require the agent to show its proposed action and wait for approval where a mistake would matter.

Why Tool Search helps

Without Tool Search, every tool definition is supplied to the model on every turn. That works for a handful of tools, but the context grows as the toolbox grows.

With Tool Search, the model begins with two capabilities:

  1. tool_search — describe the capability it needs.
  2. call_tool — invoke the matching tool with the right inputs.

When the user asks about oat milk, the agent searches for “check ingredient availability,” receives the matching tool, and then calls it. The agent does not need the schemas for unrelated tools such as payroll or delivery tracking in its context.

Big box, tiny context: add useful tools without making every agent turn carry the entire box.

Build in small, testable layers

  1. Create three read-only tools. Pick a single scenario and use predictable sample data.
  2. Write descriptions for discovery. Phrase them in the words a person—or an agent—would use to ask for the capability.
  3. Connect Tool Search. Let the agent find tools by intent instead of pinning every schema.
  4. Test normal and awkward requests. Try vague wording, missing details, and requests that should not trigger an action.
  5. Add guardrails before actions. Validate inputs, scope permissions, log calls, and use approval gates for consequential operations.

Give the agent a simple operating rule

Your agent instructions should set a repeatable loop: understand the request, search for one relevant tool, call it, inspect the result, and then decide what to do next. Do not let the agent guess when a tool can provide the answer.

For each request:
1. Search for the capability you need.
2. Call one relevant tool.
3. Use the result to choose the next step.
4. Ask for confirmation before consequential actions.

Learn from the included demos

This repository’s local demos run without Azure or an API key, making them a useful place to see the pattern before connecting real systems. Clone the repository, choose a demo, and run make demo.

  • Pizza Shop Ops demonstrates approval-gated actions.
  • The Squad Room shows multiple agent roles sharing one governed toolbox.

Your first success criteria

A beginner toolbox is working when the agent can find the correct tool from a natural-language request, use its result accurately, and decline or escalate requests outside its permissions. Add tools one at a time, keep their purposes distinct, and treat every new action as a safety decision—not just a coding task.
